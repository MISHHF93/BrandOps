## 1. Canonical loop status

> Create/Improve Twin → Ask → Artifact → Convert to Plan → Review/Approve → Execute → Verify → Learn

Both EXECUTING and VERIFYING are now producible from real plan state:

- `EXECUTING` is real for plans: `planExecutor.ts:95-253` (`executePlan`) emits `plan.execution_started` (EXECUTING) → per-step `plan.step_executed` → `plan.execution_completed`/`plan.execution_blocked`, and an "Execute" secondary action is wired to it for approved plans (`MobileWorkspaceHubView.tsx` `savedPlanToFeedItem`, `mobileApp.tsx` `executeApprovedPlan`). The executor is honest — steps needing a platform/approval/external action are recorded as BLOCKED and never performed.
- `VERIFYING` is real for plans (2026-08-17): `planVerifier.ts:106-216` (`verifyPlanOutcomes`) emits a `plan.verified` VERIFYING→COMPLETED checkpoint pair, sets per-step `done`/`failed` status from operator-confirmed outcomes only (unconfirmed steps stay unconfirmed, nothing is auto-marked achieved), and flips `Plan.status` to `verified`. A "Confirm outcomes" secondary action on `executed` plans (`MobileWorkspaceHubView.tsx` `savedPlanToFeedItem`) opens `VerifyPlanOutcomesDrawer.tsx`, which calls `mobileApp.tsx` `recordPlanVerification`. `executed` plans are deliberately not terminal in the feed (`savedPlanFeedKind`) until verified. Tested (`planVerifier.test.ts`).
- "Verify" was previously only a label attached _inside_ approval (`checkpointActions.ts:71-79`); that label is unchanged and still describes approval, not outcome verification — the two are now distinct, both real stages.

Everything else in the loop is real and event-driven (see matrix). The checkpoint ledger is honest: **no generator writes facts no backend produced.** The gaps are reachability of EXECUTE/VERIFY, not fabrication.

## 6. Security notes

- Agent tokens: SHA-256 hashed, raw never persisted (`sessions.ts:27-40`). Revocation immediate.
- Prompt-injection gate on all agent tool args (audited, `gateway.ts:484`).
- Bridge envelope: HMAC + timing-safe compare + nonce replay guard + clock-skew check (`bridge-proxy.mjs`, `bridgeReplayGuard.ts`). Fixed-window per-IP rate limit on all inbound POSTs (`BRIDGE_RATE_LIMIT`, `bridge-proxy.mjs`); MCP stdio + gateway are local-process surfaces.
- Secrets stored plaintext in `chrome.storage.local`/`localStorage` (acknowledged in `aiSecretsAccess.ts:7-8`), not a keychain.
- No secrets hardcoded in source.
- Ask text is the user's own prompt to their own Twin; the injection screen is intentionally scoped to external-agent input. The real untrusted boundary is _retrieved external content_, which is not yet ingested (no web/document retrieval ships).
