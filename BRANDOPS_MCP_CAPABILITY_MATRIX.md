Governed by `BRANDOPS_MCP_GATEWAY_DIRECTIVE.md`.

---

## 1. How to read this

- **Capability** is the canonical authorization unit. **MCP tool** is only its protocol name.
  A capability with no registry entry cannot be exposed, so this table is the complete surface.
- **Tier** drives the risk ladder: `READ` -> `GENERATE` -> `PREPARE` -> `EXTERNAL_ACTION` ->
  `SENSITIVE_ACTION`.
- **Approval** — `approval-gated` capabilities fail closed: the handler's only legal output is a
  pending proposal carrying a `NEEDS_APPROVAL` checkpoint. If it produces anything else the
  gateway rejects the whole call (`gateway.ts`, P1-4 invariant).
- **Access** — `read` capabilities are the only ones a read-only session may be granted, derived
  from the registry's `readOnly` flag.
- **Intent** — the User Intent Contract obligation. `required` means the client must declare
  `intent.objective` and `intent.reason` (plus `intent.confirm: true` for `SENSITIVE_ACTION`);
  `synthesized` means BrandOps derives and audits one when the client omits it.

## 3. Cross-cutting behavior

These hold for every row, so they are stated once rather than repeated 40 times.

| Property              | Behavior                                                                                                                                                                                                                                                                                                                                                   | Source                                                           |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| Authorization         | Bearer token -> SHA-256 hash -> session -> per-session capability grant. An ungranted capability is rejected before dispatch.                                                                                                                                                                                                                              | `sessions.ts`, `gateway.ts`                                      |
| Injection screening   | Every call's args are scanned; a match rejects the call and is audited.                                                                                                                                                                                                                                                                                    | `validation.ts`                                                  |
| Idempotency           | Optional `idempotencyKey`, scoped to (session, capability, key). A replay returns the stored result instead of re-running.                                                                                                                                                                                                                                 | `idempotency.ts`                                                 |
| Audit                 | Every call — success, failure, or block — appends an audit entry with capability, operation, latency, request preview, and the intent contract where one applies.                                                                                                                                                                                          | `audit.ts`, `gateway.ts`                                         |
| Checkpoint + trace    | Every successful call emits an operator trace and a checkpoint bound to the conversation.                                                                                                                                                                                                                                                                  | `operatorTraces.ts`, `checkpointStore.ts`                        |
| Trust tier on writes  | Agent-supplied content enters as `AGENT_REPORTED` at most, and never auto-promotes to verified Twin state.                                                                                                                                                                                                                                                 | `events.ts`, `proposals.ts`                                      |
| Memory Firewall       | Writes only. Agent-authored text is sanitized, classified by provenance (`external-agent-message` → `EXTERNAL_SOURCE`, never verified) and scored for instruction risk before dispatch. A firewall `reject` refuses the call and writes nothing; every other verdict is recorded in the audit entry. Reads are not screened — a read cannot poison memory. | `memoryScreen.ts`, `memoryFirewall.ts`                           |
| Argument contract     | What a schema declares `required` is enforced; what it documents is sufficient to call the tool; what a handler reads is declared. A "one of these two ids" rule is stated as `anyOf`, never implied by an empty `required`. All three directions are invariants.                                                                                          | `mcp/server.ts`, `mcpToolContract.test.ts`                       |
| Provenance references | A reference matching a published resource template is an **address** (fetchable via `resources/read`); anything else is a **citation** — it says which record a claim came from, for a person to audit, and is not fetchable. A test fails on any shape classified as neither.                                                                             | `mcp/resources.ts`                                               |
| Resources             | `resources/list` returns singletons only; ids are reachable by template. Each URI maps to a capability and reads through the same gateway, so identity, policy, rate limit and audit all apply.                                                                                                                                                            | `mcp/resources.ts`, `mcp/server.ts`                              |
| Response schema       | Every tool declares an `outputSchema` (JSON Schema 2020-12) and every `tools/call` returns `structuredContent` **validated against it before emission**. `capabilityId` is a `const`; `ok: false` requires `errorCode`. A non-conforming result withholds `structuredContent` and says so in-band rather than shipping a payload that broke the contract.  | `mcp/outputSchema.ts`, `mcp/server.ts`                           |
| Promotion             | Two capabilities promote agent-reported content into verified state — `builder.achievements.verify` and `builder.twin-proposals.accept`. Both are approval-gated: the agent's call creates a `promotion` proposal and changes nothing. A person approving performs the effect through `builder/promotions.ts`; rejecting performs none.                    | `capabilityRegistry.ts`, `proposals.ts`, `builder/promotions.ts` |
| Handler failure       | An exception inside a capability handler becomes a fail-closed refusal (`handler_error`) with the exception text in the audit summary and a generic message to the caller. No call escapes the ledger by crashing.                                                                                                                                         | `gateway.ts`                                                     |
| Policy                | One verdict per call from `evaluateAgentPolicy`: session live → workspace scope → capability grant → trust ceiling → rate limit → tier obligations. Every check can only deny. The verdict and the checks that ran are written into the audit entry.                                                                                                       | `policyEngine.ts`                                                |
| Trust ceiling         | `session.trustCeiling` caps effective trust below what the grants imply, and survives a reload. It can only restrict.                                                                                                                                                                                                                                      | `policyEngine.ts`, `storage.ts`                                  |
| Rate limit            | Per session, per tier, per minute: READ 120, GENERATE 60, PREPARE 30, EXTERNAL_ACTION 10, SENSITIVE_ACTION 3. **In-memory and per-process** — a local abuse brake, not a distributed quota.                                                                                                                                                                | `policyEngine.ts`                                                |
| Discovery scope       | `tools/list` returns only the calling session's granted capabilities; the active Profession Pack orders (never hides) the result.                                                                                                                                                                                                                          | `mcp/server.ts`                                                  |
| Transports            | stdio (`scripts/mcp-gateway.mjs`) and Streamable HTTP (`scripts/mcp-http-gateway.mjs`, `npm run mcp:http`). Both route through one `dispatchMcpMethod`, so every row behaves identically on either binding.                                                                                                                                                | `mcp/server.ts`, `mcp/httpTransport.ts`                          |
| Protocol versions     | `2026-07-28` (stateless per-request `_meta`), `2025-06-18`, `2025-03-26`; negotiated per request, legacy `initialize` still answered.                                                                                                                                                                                                                      | `mcp/protocol.ts`                                                |
| HTTP authorization    | Per-request `Authorization: Bearer`. 401 carries `resource_metadata`; a capability the session lacks yields 403 `insufficient_scope` naming that capability. Origin validated (403), localhost-only bind by default.                                                                                                                                       | `mcp/httpTransport.ts`                                           |
| Deployment status     | **Remote-capable, not deployment-ready.** No TLS, no OAuth authorization server integrated, sessions still loaded from an exported workspace JSON. Tracked as G1 (PARTIAL).                                                                                                                                                                                | `scripts/mcp-http-gateway.mjs`                                   |
| Tasks extension       | `io.modelcontextprotocol/tasks` advertised on `initialize` when the host wires task handlers. `tasks/get`, `tasks/cancel`, `tasks/update` served. A task-augmented `tools/call` (client capability in `params._meta`) returns `CreateTaskResult`; clients that do not opt in get ordinary content.                                                         | `mcp/server.ts`, `mcp/tasks.ts`                                  |

## 4. Response shape and verification, by group

Every response below arrives inside one envelope — `ok`, `capabilityId`, `data`, `checkpointIds`,
`auditEntryId`, plus `errorCode` on refusal — delivered as both `structuredContent` and a
serialized text block that are the same value. The "Response carries" column describes `data`.

| Group                                                 | Response carries                                                                                                                                    | How a caller verifies it                                                                                                                                                                                      |
| ----------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Context / evidence / authority reads                  | Items with `provenanceRef`, `trustTier`, `trustLabel`, and an explicit `limitations` list                                                           | Follow `provenanceRef` into the workspace; treat anything not `USER_VERIFIED` / `BRANDOPS_VERIFIED` as unconfirmed                                                                                            |
| Goals / projects / artifacts / plans / receipts reads | Canonical entity fields, ids included                                                                                                               | Re-read by id; receipts additionally record `userAction` and `timestamp`                                                                                                                                      |
| Voice                                                 | `toneOfVoice`, `positioning`, `targetAudience`, the user's own `voiceExamples`, `highConfidenceClaims`, `trustTier`, `provenanceRef`, `limitations` | Examples are the user's own writing, so `USER_VERIFIED` is a fact about provenance, not a quality claim. BrandOps stores one voice; the `channel` argument is echoed and the response says it changed nothing |
| Relationship context                                  | Stage, status, `lastContactAt`, what is `outstanding`, and up to five recorded interactions                                                         | The working state of the relationship, not a dossier: the contact's free-form notes field is deliberately absent, and `limitations` says so                                                                   |
| Next best actions                                     | Ranked items with `urgency`, `confidence`, `reason`, `signals`, `command`                                                                           | `command` is the canonical entry point that starts the work                                                                                                                                                   |
| Proposals (achievement, artifact, twin, opportunity)  | `proposalId` / `eventId` plus `status: pending`                                                                                                     | The proposal appears in the review queue; nothing is applied until a user decides                                                                                                                             |
| Plan conversion                                       | `planId` and the compiled draft                                                                                                                     | Read back with `brandops_get_plan_status`                                                                                                                                                                     |
| Approval-gated actions                                | `proposalId`, `status: pending`, and a note that nothing executed                                                                                   | A `NEEDS_APPROVAL` checkpoint exists with `receiptRef` = proposal id                                                                                                                                          |
| Durable execution                                     | `taskId` plus a protocol task: `status`, `statusMessage`, `ttlMs`, `pollIntervalMs`, and `inputRequests` / `result` / `error`                       | Poll `tasks/get` or `brandops_get_execution`. The task is a projection of Plan/Checkpoint state, so it cannot disagree with the execution it describes                                                        |
| Outcome reporting                                     | `outcomeId`, `dimension`, `score`, `trustTier: AGENT_REPORTED`                                                                                      | Recorded under `builderActivity.outcomeScores` with `notedBy` naming the reporting agent                                                                                                                      |

## 5. Known limits of this matrix

1. **Output schemas declare the envelope exactly and the payload conservatively.** `data` is
   pinned only as deeply as a handler actually constructs it; where a handler forwards a service's
   return value, the schema names the top-level keys and stops. That is deliberate — a schema that
   over-promises is worse than one that says less, because the client validates against it.
2. **The validator is a subset, not a draft-2020-12 implementation.** It honors `type`, `const`,
   `enum`, `properties`, `required`, `additionalProperties`, `items`, `anyOf`, `allOf` and
   `if`/`then`/`else`, and ignores keywords it does not implement rather than inventing failures.
   The declared schemas use only what it supports.
3. **No per-capability rate limits** (G11). Budgets are per tier.
4. **Discovery is scoped by grants, not by connected systems or feature flags.** A session sees
   only what it was granted, and the Profession Pack orders the surface — but a tool whose
   underlying connector is absent is still advertised (the remainder of G12).
5. **Live interoperability is UNVERIFIED against third-party clients.** Both gateway processes
   _have_ been driven end to end over real JSON-RPC — stdio (tasks extension advertised, a
   task-augmented `tools/call` returning `CreateTaskResult`, `tasks/get`, `tasks/update` refusing
   an agent-side approval, `tasks/cancel`) and HTTP (unauthenticated metadata discovery, 401
   challenge, 403 `insufficient_scope` step-up, 405 on GET, 403 on a foreign Origin, an authorized
   `tools/list`, and the full durable-execution round trip). That is our own transport, not a
   second vendor's client. Coverage is otherwise contract tests (`mcpProtocol.test.ts`,
   `mcpHttpTransport.test.ts`) plus capability tests (`mcpPhase1Capabilities.test.ts`,
   `mcpDurableExecution.test.ts`).
